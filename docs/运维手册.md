# AI 客服系统 — 运维与离职交接手册

本文在**原《运维手册》**基础上扩容，同时服务两类读者：

| 读者 | 用途 |
|------|------|
| **日常运维** | Docker / `kb.py` / 巡检 / 备份 / 迁移等命令速查 |
| **离职、轮岗、长假交接** | 接手人按清单核对权限与资产，避免「人走线断」 |

**说明**：本文**不**承载真实密码、Token、私钥；交接时由负责人通过**安全渠道**单独移交，并在公司指定位置（如密码柜、密钥管理系统）登记。

---

## 一、离职 / 轮岗交接清单（接手人逐项打勾）

建议在离职或轮岗**前 5～10 个工作日**启动，由**交接人 + 接手人 + 直属负责人**三方确认。

### 1.1 代码与制品

- [ ] **GitLab（或等价）**：仓库 `ai-customer-service` 的 **Developer/Maintainer** 已转移给接手人；**Deploy Key / CI Token** 已更新或轮换。
- [ ] **默认分支 / 发版标签**：当前生产使用的 **分支或 Tag**（如 `v1.0.0`）已书面确认。
- [ ] **本手册与 `scripts/kb/README.md`**：接手人已通读，知道**高危命令**（`rebuild`、`delete` 全库）必须先 **dry-run**。

### 1.2 云与网络

- [ ] **云厂商子账号 / RAM**：ECS、VPC、安全组、弹性公网 IP 的**登录入口与 MFA** 已移交。
- [ ] **安全组规则**：API（如 **8000**）、SSH（**22**）及**内网 PG / Milvus / Redis / ES** 的放通策略已记录；变更流程已知会。
- [ ] **域名与证书**：若有 Nginx / HTTPS，**证书到期时间**与续签责任人已写明。

### 1.3 运行时与配置（服务器上的 `.env`）

- [ ] **`.env` 路径**（如 `/opt/aisales/.env`）与**备份方式**（仅备份到安全介质，**不入 Git**）。
- [ ] **PostgreSQL / Milvus**：主机、库名、账号责任方；**迁移命令** `python scripts/migrate.py upgrade` 已在接手环境跑通。
- [ ] **Ollama（若用本地嵌入）**：安装方式（`systemd` / 二进制路径）、**模型名**（如 `bge-m3`）、数据目录（如 `~/.ollama`）。
- [ ] **Redis / Elasticsearch**：若生产依赖，**内网可达地址**与客户端依赖（如 `pip install elasticsearch`）已确认；若暂不用，**降级行为**（进程内限流、空历史）已告知业务方。
- [ ] **业务后端 `BACKEND_BASE_URL`**：当前统一前缀（如 `https://sales.xinjixiu.com.cn/prod-api`）及变更联系人。

### 1.4 进程与发布

- [ ] **API 启动方式**：Docker Compose **或** 裸机 `uvicorn` / **systemd** 单元文件名与 **`restart` 命令**。
- [ ] **Ollama / 其他常驻服务**：是否与 API 同机、是否 **systemd** 保活。
- [ ] **发版窗口与回滚**：最近一次成功发版的 **Git 提交 / 镜像 Tag**；回滚步骤（`git checkout` + 重启 / 镜像回滚）已演练或文档化。

### 1.5 账号回收（离职当日）

- [ ] 云控制台、GitLab、JumpServer/堡垒机、企业微信机器人等 **与本人绑定的账号** 已禁用或改密。
- [ ] **个人 SSH 公钥** 从服务器 `authorized_keys`、GitLab **SSH Keys** 中移除（改用接手人或 CI 密钥）。

## 三、接手后验证顺序（建议 30 分钟内完成）

在**已拿到 `.env`、已激活 venv** 的前提下（路径按实际调整）：

```bash
cd /opt/aisales
. .venv/bin/activate
python scripts/ops/healthcheck.py
python scripts/migrate.py current
python scripts/kb.py status
curl -sS http://127.0.0.1:8000/health | head
```

- **Docker 部署**：将上述命令中的路径改为 `docker compose exec api-1 …`（见下文「服务管理」）。
- 若 `healthcheck` 中某项为 `error`，对照 **第二节** 核对网络与配置；**Redis 暂不可用**时可能仍为 `success: false`，需与业务约定是否必须修复。

## 四、裸机部署补充（与 Docker 二选一或并存）

若生产为 **ECS 上直接 `uvicorn` + 本机 Ollama**（非 Compose），交接时需额外写明：

| 项 | 说明 |
|----|------|
| 代码目录 | 如 `/opt/aisales` |
| 虚拟环境 | `.venv` 激活方式（注意部分 shell 无 `source`，用 `. .venv/bin/activate`） |
| API | `uvicorn api.main:app --host 0.0.0.0 --port 8000` 或 **systemd** |
| Ollama | `systemctl` 或 `ollama serve`；**勿多实例冲突** |
| 公网访问 | 安全组放行 **API 端口**（如 8000） |
| 知识库入库 | 宿主机：`python scripts/kb.py …`（无需 `docker compose exec`） |

## 六、服务管理（Docker Compose）

服务名与 `docker-compose.yml` 一致：`api-1` ~ `api-3`、`postgres`、`redis`、`milvus-standalone`、`ollama`、`nginx` 等。

```bash
# 启动全部
docker compose up -d

# 停止（保留数据卷）
docker compose down

# 仅重启 API（代码热更新后）
docker compose restart api-1 api-2 api-3

# 查看 API 日志
docker compose logs -f api-1 api-2 api-3 --tail 200
docker compose logs --since 30m api-1
```

**更新部署（示例）**：

```bash
git fetch origin && git checkout <分支或标签> && git pull
docker compose build
docker compose up -d --no-deps api-1 api-2 api-3
```

**扩缩容**：增加 `api-4` 等需在 `docker-compose.yml` 与 `deploy/nginx.conf` 的 upstream 中同步修改；勿仅用 `--scale` 若与当前 Nginx 配置不一致。

## 七、知识库管理（`scripts/kb.py`）

**均在 API 容器内执行**（与生产配置、网络一致）：

```bash
docker compose exec api-1 python scripts/kb.py <子命令> [参数]
```

### 7.1 查询

```bash
docker compose exec api-1 python scripts/kb.py status
docker compose exec api-1 python scripts/kb.py status --collections products,sales_script

docker compose exec api-1 python scripts/kb.py list --collection products
docker compose exec api-1 python scripts/kb.py list --collection sales_script --limit 500
```

**注意**：`status` 中 Milvus `num_entities` 在 delete/replace 后常为近似值；**按文件对账以 `list --collection`（PG）为准**。

### 7.2 增量 / 替换入库

**产品（`products`）**：路径在 `product/…` 时会推断为 `products`；**必须**提供 `--category`（Milvus 元数据），或设置环境变量 `KB_PRODUCTS_DEFAULT_CATEGORY`。

```bash
# 推荐：单文件替换
docker compose exec api-1 python scripts/kb.py ingest \
  product/新肌秀舒净雅香沐浴乳/新肌秀舒净雅香沐浴乳_知识库.md \
  --category "沐浴乳" --replace

# 干跑
docker compose exec api-1 python scripts/kb.py ingest \
  product/新肌秀舒净雅香沐浴乳/新肌秀舒净雅香沐浴乳_知识库.md \
  --category "沐浴乳" --replace --dry-run
```

**话术（`sales_script`）**：

```bash
docker compose exec api-1 python scripts/kb.py ingest data/sales_scripts --replace
docker compose exec api-1 python scripts/kb.py ingest data/sales_scripts --dry-run
```

### 7.3 全量重建（高危）

会 **DELETE PG + drop Milvus** 对应 collection，再按标准路径重灌。**务必先 dry-run**。

```bash
docker compose exec api-1 python scripts/kb.py rebuild --products --scripts --dry-run
docker compose exec api-1 python scripts/kb.py rebuild --products --scripts
```

### 7.4 删除

```bash
# 按 source_file 删除 PG + Milvus 中该文件对应块
docker compose exec api-1 python scripts/kb.py delete --collection products --source "某产品_知识库.md"

# 清空整个 collection（极危险）
docker compose exec api-1 python scripts/kb.py delete --collection products --dry-run
docker compose exec api-1 python scripts/kb.py delete --collection products
```

### 7.5 暂存区（可选）

```bash
docker compose exec api-1 python scripts/kb.py staging upload /path/to/文件.docx \
  --collection products --doc-type product --category "沐浴乳"
docker compose exec api-1 python scripts/kb.py staging list
docker compose exec api-1 python scripts/kb.py staging process
docker compose exec api-1 python scripts/kb.py staging process --dry-run
```

### 7.6 兼容入口

- `python scripts/rebuild_standard_knowledge.py` → 内部调用 `kb.rebuild_std`
- `python scripts/ingest_sales_scripts.py --source data/sales_scripts …` → 内部委托 `kb ingest`

## 八、Makefile 快捷命令（仓库根）

需 **GNU Make**。可通过变量覆盖默认值，例如：`make build-update GIT_REF=v1.0.0`。

| 目标 | 作用 |
|------|------|
| `make deploy` | `docker compose up -d` |
| `make down` | `docker compose down` |
| `make restart-api` | 重启 `api-1` ~ `api-3` |
| `make build-update` | 拉代码 + build + 滚动更新 API |
| `make kb-status` | 容器内 `kb.py status` |
| `make kb-list-products` | `kb.py list --collection products` |
| `make kb-ingest-products` | 示例产品路径 + `--category` + `--replace` |
| `make kb-ingest-products-dry` | 同上 `--dry-run` |
| `make kb-ingest-scripts` | 话术目录 `--replace` |
| `make kb-ingest-scripts-dry` | 话术 dry-run |
| `make kb-rebuild` / `kb-rebuild-dry` | 全量重建 / dry-run |
| `make health` | `scripts/ops/healthcheck.py` |
| `make health-pretty` | 巡检 + 请求本机 `http://127.0.0.1:8000/health` |
| `make logs` | 跟踪 API 日志 |
| `make backup-pg` | `pg_dump` 写入 `backups/` |
| `make backup-milvus-report` | Milvus 元数据 JSON 报告 |
| `make migrate-check` / `migrate-upgrade` | Alembic |
| `make clean-checkpoints` | 清理不活跃 checkpoint |
| `make test` | 对话 + 情绪边界脚本 |
| `make test-rag` | RAG 质量脚本 |

`Makefile` 内产品路径、分支名可按项目实际修改。

## 九、一键巡检（`scripts/ops/healthcheck.py`）

检查 PostgreSQL、Milvus、Redis、Ollama（若配置为 ollama）；输出 **JSON**，任一项 `error` 时 **退出码 1**。

```bash
docker compose exec api-1 python scripts/ops/healthcheck.py
docker compose exec api-1 python scripts/ops/healthcheck.py --no-pretty
docker compose exec api-1 python scripts/ops/healthcheck.py --api-url http://127.0.0.1:8000
```

## 十、备份（`scripts/ops/backup.py`）

| 子命令 | 说明 |
|--------|------|
| `pg-dump --out FILE [--gzip]` | 经 `docker compose exec postgres pg_dump` 导出逻辑库 |
| `pg-restore --in FILE` | 经 `psql` 导入（**覆盖数据**；`.sql.gz` 支持） |
| `milvus-report --out FILE.json` | 各 collection 的 `get_collection_stats` 元数据 |

```bash
docker compose exec api-1 python scripts/ops/backup.py milvus-report --out backups/milvus_report.json
```

**Milvus 向量全量**依赖 Docker 卷快照或 Milvus 官方备份方案；`milvus-report` 仅作留痕与对账辅助。

**仅 PostgreSQL、在宿主机用 compose**（与 `Makefile` 的 `backup-pg` 类似）：

```bash
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backups/agent_db_$(date +%Y%m%d).sql
```

## 十四、典型流程速查

**更新一篇产品知识库**：编辑 md → `kb ingest … --category … --dry-run` → `--replace` → `kb list` / `verify_rag_quality`。

**发版**：`build-update` → `migrate-check` → `migrate-upgrade`（维护窗口）→ `restart-api` → `health`。

**灾备前**：`backup-pg` + `milvus-report`（或卷快照）。
